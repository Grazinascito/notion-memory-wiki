# Notion Memory Wiki Architectural Research Decisions

> Pre-Design-Doc technical study answering [PRD.md](file:///Users/grazinascimento/Documents/random_projects/notion-memory-wiki/PRD.md) Section 9 and Section 10 (Questions 1, 3, 4, and 5).
> Fixed PRD constraints obeyed across every recommendation: zero internal Large Language Model (LLM) calls in core operations, Level 0 startup context under 1,500 tokens including tool definitions, Notion always wins on schema or content drift, zero `Autonomous External Actions`, and explicit user approval before any `Destructive Action` or Notion schema change.

## Workspace Baseline (Verified Aggregate Shape)

Python inspection of [wiki-raw-extraction-2026-11-22.json](file:///Users/grazinascimento/Documents/random_projects/notion-memory-wiki/docs/wiki-raw-extraction-2026-11-22.json) (874,907 bytes across 126 Notion calls, 108 fetches, 18 queries, and 1 error) shows the structural scale of a real custom workspace:

- The root is a native Notion Wiki database (`type: database`, `wiki: true`) whose home content holds 23 child pages and 9 database tags (8 with `data-source-url` links). Across 36 fetched items (29 regular pages plus database fetches) sit 92 `<database>` tags, and 63 of them reference inline linked views inside hub pages such as `Project management`, `Goals e OKRs`, `Resource Library`, `Inbox`, `Empregabilidade e Carreira`, and `Daily Habits v2`.
- The 61 parsed `<data-source-state>` schemas (56 unique `collection://` URLs) hold 647 total properties (min 3, mean 10.61, max 49), 129 `relation` properties, and 939 options across 147 `select`, `multi_select`, and `status` fields (up to 52 options in one field). Exactly 90 fields are strictly read-only (`formula`: 50, `created_time`: 14, `button`: 10, `last_edited_time`: 6, `rollup`: 6, `created_by`: 3, `auto_increment_id`: 1), plus 2 writable Wiki `verification` fields.
- Raw `collection://` schema fetches total 359,368 characters (about 89,842 tokens). The 8 `Agent Operating Guide` pages total 48,529 characters (about 12,132 tokens, with 38,561 characters across the 7 prose pages). Eager loading of schemas or guides cannot fit under 1,500 tokens.

## 2. Decision 1 (Ontology Representation and Modeling)

### External Ontology Modeling References Beyond the 12 Repositories
1. **Noy and McGuinness (Stanford), *Ontology Development 101*:** Middle-out, competency-question-driven modeling with minimal ontological commitment. Every modeled field must directly serve the 5 verbatim scenarios in `PRD.md` lines 112 to 116 rather than cataloging unused Notion attributes.
2. **W3C SKOS (Simple Knowledge Organization System) and W3C SHACL (Shapes Constraint Language):** SKOS concepts (`broader`, `narrower`, `prefLabel`, `altLabel`) fit hierarchical workspace `Taxonomy` (areas, hub pages, and `Agent Operating Guide` pages). SHACL closed-world constraint shapes fit deterministic write `Validation` against Notion schemas. OWL (Web Ontology Language) relies on open-world inference and mismatches closed relational Notion databases.
3. **Palantir Foundry Ontology (Semantic and Kinetic layers):** Splits domain modeling into a Semantic layer (`ObjectType`, typed `Property`, directed `LinkType`, mirrored in `cortexdb`) and a Kinetic layer (`ActionType` with pre-commit validation and approval rules), mapping directly onto additive vs `Destructive Action` governance.
4. **LinkML (Linked Data Modeling Language):** Shows how human-readable YAML schema definitions compile to deterministic runtime validators and portable starter templates.
5. **Notion *A New Shape for Work* plus PARA (Projects, Areas, Resources, Archives) and GTD (Getting Things Done):** Grounds the optional blank-workspace starter ontology without forcing database renames on custom existing workspaces.

### Comparison of 3 Distinct Approaches

| Criterion | Option 1A: Layered Declarative Semantic-Kinetic Model (Recommended) | Option 1B: Full Semantic Web Triple Store (RDF, OWL-RL, SPARQL, Cypher) | Option 1C: Flat Workspace Registry JSON (`workspace.json`) |
|---|---|---|---|
| `Taxonomy` representation | SKOS-style tree of areas, hub pages, linked-view mounts, and guide pages with `prefLabel` and `altLabel` aliases. | RDF (Resource Description Framework) triples with RDFS class hierarchies. | Flat list of database titles and IDs with no area hierarchy. |
| `Ontology` and `Knowledge Graph` | Extracted Notion `ObjectType` (`database_id`, `data_source_id`, properties, options, `read_only`, `schema_hash`) + directed `LinkType` edges + human-editable `ontology.yaml` overlay (`purpose`, `area`, `extra_required_fields`, `excluded`, `agent_scopes`). | Full triple store + OWL/SHACL reasoner (`cortexdb/pkg/graph` style, 75+ files). | Flat schema dump that drops typed directed relation edges and scope checks across hops. |
| Level 2 `Fractal Structure` | Separate `fractal_pointers` store (`parent_page_id`, `child_database_id`, `child_data_source_id`, `title`, `discovered_at`) learned lazily on record open, spending 0 tokens at Level 0 and Level 1. | Dynamically asserted RDF subgraphs that are hard to prune when Notion drifts. | Not modeled, forcing either flat discovery bloat or blind runtime crawls. |
| Custom vs starter workspaces | Prescribed+extracted (`strict` enforcement) on confirmed core DBs (`graphiti` hybrid pattern) + optional LinkML-style 6-DB starter kit for blank workspaces. | Heavy upfront ontology authoring required before value appears. | Handles custom names loosely, but gives no structured starter ontology. |
| Drift resilience | High because the machine-synced Notion snapshot overwrites cleanly while `ontology.yaml` user metadata survives drift. | Low because ontology inference rules break when users rename columns in Notion. | Medium because regeneration is simple, but loses user rules and graph relations. |

**Recommendation (Option 1A):** Adopt the **Layered Declarative Semantic-Kinetic Model**. Keep machine-synced Notion metadata strictly separate from user-authored `ontology.yaml` overlays so Notion always wins on schema drift while user aliases, purposes, `extra_required_fields`, `capture_inbox_id`, `guide_pages`, and `agent_scopes` remain intact. For blank workspaces, offer an opt-in LinkML-style 6-database starter ontology (`Projects`, `Tasks`, `Goals`, `Resources`, `Decisions`, `Capture Inbox`) with typed `LinkTypes` and a 4-page starter `Agent Operating Guide`, created only after explicit user confirmation.

## 3. Decision 2 (Agent Integration Surface and Sub-1,500-Token Level 0 Budget)

### Direct Notion REST API vs Wrapping `ntn` and Auth Isolation
Call the Notion REST (Representational State Transfer) Application Programming Interface (API) directly instead of wrapping the `ntn` CLI. `notion-axi` spawns `ntn` per API call (`src/ntn.ts:27-55,93-98`) and regex-parses stderr without handling HTTP 429 (`src/ntn.ts:114-156`). Direct REST removes an external binary dependency, exposes raw HTTP 429 `Retry-After` and `additional_data.rate_limit_reason` headers, and lets us default to **internal integration tokens** (`notion.so/profile/integrations`). As `makenotion/lore/docs/authentication.md:28-44` confirms, both `ntn login` and Personal Access Tokens (`developers/tokens`) execute with the human user's full workspace permissions, breaking Notion's native page-sharing boundary. Internal integration tokens enforce hard page-sharing isolation and support separate per-agent integrations when strict credential isolation is desired, while PATs remain opt-in only with an explicit warning.

### Comparison of 3 Agent Surfaces
- **Option 2A (AXI-Style CLI + Single Runtime `SKILL.md` Only):** Lowest startup footprint at 735 to 1,055 tokens. Verified `notion-axi` benchmarks (45 headless Claude Sonnet 4.6 runs against `makenotion/notion-mcp-server`, 100% success across conditions) recorded ~63,300 average input tokens, USD 0.063, 2.8 turns, and 11s for `notion-axi` compared to ~177,900 tokens, USD 0.191, 5.4 turns, and 34s for Notion MCP (~3x cheaper overall and ~3.6x on complex multi-step tasks). Works naturally in shell cronjobs (`PRD.md` Story 5), but excludes shell-less MCP-only clients.
- **Option 2B (Thin 4-to-5-Tool MCP Server Only):** Provides native `readOnlyHint`, `destructiveHint`, and `idempotentHint` host prompts plus process-pinned `--profile`. However, real MCP schemas bloat quickly because `okf-agent-memory`'s 7-tool `tools.json` uses 22,360 chars (~5,590 tokens), and `lazy-tool`'s bare-minimum 5 meta-tools measure 915 tokens (`README.md:490-496`). Four polymorphic tools realistically cost 550 to 1,000 tokens unless `outputSchema` is omitted and parameters stay flat, leaving tight headroom under 1,500 tokens. MCP `InitializeResult.instructions` is also inconsistently injected across hosts, and MCP fits poorly inside user cronjobs.
- **Option 2C (Shared In-Process `core/` Library with AXI CLI + Skill in v1.0 and Optional Thin 4-Tool MCP in v1.1) [Recommended]:** Ship one surface first so v1.0 avoids `lore`'s dual-surface parity overhead and `notion-cli-agent/src/mcp.ts:48-60`'s `execFileSync` shell-out anti-pattern. Keep `core/` transport-agnostic so a thin ~250-line in-process MCP adapter (`wiki_catalog`, `wiki_read`, `wiki_write` with `destructiveHint: false`, `wiki_destructive` with `destructiveHint: true`) can ship in v1.1 under a hard CI cap of 600 tokens total across all tool schemas.

### Concrete Level 0 Token Budget and Delivery Mechanism
Static `agentskills.io` `SKILL.md` frontmatter loads only `name` and `description` at startup, so it cannot dynamically inject a user's workspace catalog or per-`Agent Scope` filter. Even `notion-axi` added `SessionStart` hooks (`src/commands/setup.ts:1-32`) for startup injection. Therefore, we fold guide refresh into **one** runtime skill (`notion-wiki/SKILL.md`, frontmatter ~90 tokens, on-demand body capped at 450 tokens) plus one removable onboarding skill (`notion-wiki-setup/SKILL.md`, ~70 tokens). Dynamic per-profile Level 0 context is delivered via a **mutually exclusive dual mechanism**, using either `wiki render --profile <name>` to write a bounded Push block into the host's startup instruction file (`AGENTS.md`, `CLAUDE.md`, `.cursor/rules`, or Hermes/OpenClaw/OpenBot/Grok Bot prompt files) or a `SessionStart` hook running `wiki wakeup --profile <name>` on hook-capable hosts, with a zero-push fallback where `SKILL.md` directs one `wiki wakeup` call on the first Notion turn.

### Single Enforcement Pipeline Inside `core/`
1. **`Agent Scope` (Hindsight Monotonic Narrowing + Environment Lock):** `Agent Scope` can only narrow the `Root Page` and Notion sharing boundary, never widen it. When `WIKI_AGENT_PROFILE` is set in the process environment (or an MCP server starts with fixed `--profile`), `core/` rejects any CLI `--agent` override with `SCOPE_LOCKED`. Scope checks run on Level 0 rendering, Level 1 reads/writes, every hop of `Knowledge Graph` relation traversal (`SCOPE_DENIED`), and guide reads (allowed unless explicitly excluded). Hard credential isolation still uses separate Notion internal integration tokens per specialist agent.
2. **Deterministic `Validation` (Zero LLM Calls):** Runs before every network write against cached Notion schemas (refreshing once on drift) to verify non-empty `title`, property types, valid `select`/`multi_select`/`status` options with case-insensitive snap to Notion's exact casing and live-row fallback (`easy-notion-mcp/README.md:635,641`), strict write-block on read-only fields (`formula`, `rollup`, `created_time`, `last_edited_time`, `created_by`, `last_edited_by`, `button`, `auto_increment_id`) while allowing writable Wiki `verification` (`state` and `date`, omitting Notion-set `verified_by`), relation target `data_source_id` plus scope check, and user `extra_required_fields` plus numeric bounds (`lore/src/policy/`). Failures return a compact `AxiError` listing only valid options for the failing field.
3. **Unforgeable `Destructive Action` and Schema-Change Gate:** Additive creates and routine structured updates (`status`, `select`, `multi_select`, `date`, `checkbox`, `relation` to non-empty valid values) run after validation. Archiving (`in_trash: true`), clearing populated properties, overwriting non-empty user prose (`PATCH /markdown` replace or `allow_deleting_content: true`), or `PATCH /v1/data_sources` schema changes halt immediately. `core/` writes a local pending proposal (`proposal_id`, exact diff, `last_edited_time` optimistic guard adapted from `basic-memory` `expected_checksum`, short expiration) and prints only the `proposal_id` and diff, never handing an executable approval token to the LLM (preventing prompt-injected self-approval). Execution requires one of three unforgeable gates: (a) the human runs `wiki approve <proposal_id>` out-of-band in their terminal, (b) dedicated `wiki approve`, `wiki destroy`, and `wiki schema-apply` subcommands sit behind host harness `ask`/deny rules, or (c) in optional MCP mode, destructive writes live in `wiki_destructive` (`destructiveHint: true`).
4. **Zero `Autonomous External Actions` and Prompt-Injection Hygiene:** The HTTP client allowlists only `api.notion.com`. All Notion prose returned to agents is wrapped in an untrusted-data boundary notice with `javascript:` and `data:` links stripped (`easy-notion-mcp/README.md:651-656`).

## 4. Decision 3 (Local Synchronized Index vs Direct Lean Notion API Queries)

### Verified Notion API `2025-09-03` and `2026-03-11` Contract Details
- Under `2025-09-03`, schemas and queries live on `/v1/data_sources/{id}` and `POST /v1/data_sources/{id}/query`, while `GET /v1/databases/{id}` returns container metadata and `data_sources[]`. Following `notion-cli-agent/src/commands/sync.ts:56-71`, store both `database_id` and `data_source_id`.
- Under `2026-03-11`, `archived` becomes `in_trash`, `after` becomes structured `position`, `transcription` becomes `meeting_notes`, and `GET`/`PATCH /v1/pages/{id}/markdown` (`markdown_version: v2`) reads or appends whole pages in 1 call. Pages over ~20,000 blocks or with unshared/unsupported blocks return `truncated: true` plus up to 50 `unknown_block_ids[]`.
- **Critical linked-view discovery finding:** `GET /v1/blocks/{id}/children` returns inline linked database views as `type: "unsupported"`, which explains why 63 linked views appeared in the 2026-11-22 hosted-MCP dump but would vanish under naive block crawling. Setup must combine 2-level `GET /v1/blocks/{id}/children` (traversing layout containers like `column_list`, `column`, `toggle`, `callout`), single-pass `POST /v1/search` (`filter: { property: "object", value: "data_source" }`), and Notion's **Views API** (`GET /v1/views?data_source_id=...`), which lists all views including linked views across the workspace.
- **Rate limits:** Free and Plus plans allow 180 req/min (~3 req/s) per connection; Business and Enterprise allow 600 req/min (~10 req/s); `query-data-source` holds a standalone ~3 req/s per-connection cap; a shared workspace pool also applies. HTTP 429 returns `Retry-After` and `additional_data.rate_limit_reason` (`public_api_request_rate_limit`, `public_api_space_request_rate_limit`, `public_api_endpoint_rate_limit`).

### Comparison of 3 Storage and Query Architectures

| Dimension | Option 3A: Disposable SQLite WAL Metadata Index + YAML Overlays + Direct Lean API (Recommended) | Option 3B: Atomic JSON/YAML Files + Lockfile + Direct Lean API (Serious v1 Alternative) | Option 3C: Zero Local Cache (Direct Notion API Every Turn) |
|---|---|---|---|
| Local footprint | Single disposable `cache.sqlite` (6 to 7 tables: `taxonomy_nodes`, `databases`, `relation_edges`, `guide_pages`, `fractal_pointers`, `pending_proposals`, `rate_limit_state` + FTS5) alongside human-editable `ontology.yaml` and `guide-summary.md`. Zero embeddings, zero SPARQL/Cypher, zero page-body mirror. | `ontology.yaml`, `schema-cache.json`, `fractal-pointers.json`, `pending-proposals.json`, `rate-limit-state.json` (atomic temp+rename `0o600` like `lore/src/notion/rate-limit.ts:906-944`), `guide-summary.md`. | Only static config with no cached schemas or pointers. |
| Fuzzy and multilingual lookup | Sub-millisecond FTS5 `trigram` + `unicode61 remove_diacritics 2` (`cortexdb/pkg/agentmem/schema.go:118-138`) handles Portuguese accents and typos offline. | Linear in-memory scan over 15 to 25 DBs (<150 KB), adequate for DBs, weaker if record title stubs grow later. | Requires live Notion search every turn, burning latency and quota. |
| Cross-process concurrency (Story 5) | SQLite WAL (Write-Ahead Logging) serializes concurrent Level 2 fractal writes, pending proposals, and HTTP 429 cooldown state across parallel specialist CLI processes. | Atomic rename works for whole-file state like `rate-limit-state.json`, but concurrent partial updates to `fractal-pointers.json` require file locks. | No shared cross-process 429 state, so parallel specialists cascade-fail. |
| Drift and migration safety | Strictly disposable because deleting `cache.sqlite` and running `wiki sync` rebuilds 100% from Notion + `ontology.yaml`, avoiding `basic-memory`'s 45-migration burden. | Zero schema migrations and human-readable `git diff`. | No cache drift, but fails `<5 min` setup and zero-blind-discovery goals. |

**Recommendation (Option 3A, keeping Option 3B under Pre-Commitment Guard review):** Use a **minimal disposable SQLite WAL index** (built-in `node:sqlite` on Node 22+ or pure-Go `modernc.org/sqlite` to avoid native C++ build friction) strictly for metadata, FTS5 alias/title lookup, typed `relation_edges`, lazy Level 2 `fractal_pointers`, `pending_proposals`, and cross-process `rate_limit_state`. Live database queries (`POST /v1/data_sources/{id}/query`) and prose reads (`GET /v1/pages/{id}/markdown`) always hit Notion directly with bounded previews and `--fields` projection.

### Notion-Wins `Context Sync` Triggers and HTTP 429 Protection
1. **Reactive refresh on mismatch or error:** Any HTTP `400 validation_error`, unknown property/option, `404`, or `last_edited_time` mismatch refreshes that single `data_source` or guide page, overwriting Notion-sourced fields while preserving `ontology.yaml` overlays and flagging deleted properties.
2. **Lazy Level 2 fractal discovery:** Opening a specific record inspects child blocks or `unknown_block_ids` for nested `child_database` items and records pointers in `fractal_pointers` with zero upfront token cost.
3. **Bounded structural sync (`wiki sync`):** Refreshes only confirmed core `data_source_id`s (~15 to 25 calls) plus `guide_pages` timestamps (~8 calls), completing in ~25 to 35 calls (~10 to 15s) instead of 126 calls and 28 minutes.
4. **Cross-process HTTP 429 protection:** Default conservative gate of 2.5 req/s sustained, burst 3, max 3 in-flight (configurable higher on Business/Enterprise while keeping `query-data-source` capped at <= 3 req/s, adapting `lore/src/notion/rate-limit.ts:137-171`). On any HTTP 429, parse `Retry-After` and `rate_limit_reason` and write `retry_after_until` into shared local state so all sibling specialist processes pause together. Off-peak maintenance runs at 1 req/s, concurrency 1, and yields whenever active-chat traffic ran within the past 60 seconds.

## 5. Decision 4 (Setup Packaging, Guide Summary Refresh, and Optional Off-Peak Maintenance)

### Portable Setup Packaging Across Agent Platforms
All 5 primary target platforms (Hermes, Claude Code, Codex, Cursor, and OpenClaw) support the open `agentskills.io` (`SKILL.md`) format, while OpenBot, Grok Bot, and custom agents support shell commands plus startup instruction blocks.

- **Option 4A (Single CLI Package + `agentskills.io` Bundle + `wiki render` + Terminal Fallback) [Recommended]:** Ship one CLI (`npx` or compiled single binary) bundling `notion-wiki/SKILL.md` (runtime) and `notion-wiki-setup/SKILL.md` (removable post-setup). `wiki render --profile <name>` writes the bounded Level 0 Push block to each platform's instruction file (or installs a `SessionStart` hook where supported). Users without a connected agent run `wiki setup <root-url>` deterministically in the terminal with zero LLM keys.
- **Option 4B (Host-Specific MCP Auto-Installers Only):** High configuration churn across 7 agent hosts, omits shell-only cronjobs, and increases Level 0 token pressure.
- **Option 4C (Prompt-Only Scripts Like `karpathy-llm-wiki`):** Cannot enforce `Agent Scope`, deterministic `Validation`, cross-process 429 pacing, or unforgeable `Destructive Action` gates.

**Guided 2-level setup flow (<5 min, 0 row queries):**
1. Verify the Notion token via `GET /v1/users/me` and detect whether the `Root Page` is a regular page (`GET /v1/pages/{id}`) or a native Wiki root (`GET /v1/databases/{id}`).
2. Run a bounded 2-level block scan combined with `POST /v1/search` (`object: "data_source"`) and `GET /v1/views?data_source_id=...` to surface both direct databases and inline linked views without reading row data.
3. Let the user confirm active core databases and linked views, exclude legacy or duplicate databases, and optionally declare aliases, purposes, `extra_required_fields`, and `Agent Scope` profiles.
4. If `Agent Operating Guide` pages exist, the user's connected agent proposes a <= 350-token `guide-summary.md` plus page index for confirmation (or `wiki setup` runs a zero-LLM extractor using top-level `H1` and second-level `H2` Markdown headings). If no guide exists, setup succeeds cleanly and offers an optional starter ontology plus starter guide template created only on explicit confirmation.

### `Agent Operating Guide` Summary Refresh Trigger
Zero silent background LLM calls ever rewrite the guide summary. `guide_pages` stores `(page_id, title, last_edited_time, summary_synced_at, user_pinned)`. During `wiki sync`, `wiki status`, or on-demand guide reads, any page with `last_edited_time > summary_synced_at` sets `summary_stale = true` and emits a 1-line notice naming the edited page. Refresh occurs only on explicit user action through one of three paths: (a) the user asks their connected agent to fetch the edited Markdown, propose an updated summary within the 420-token cap, and write it after confirmation; (b) the user edits `guide-summary.md` directly (setting `user_pinned: true` to block automated proposals); or (c) zero-LLM `wiki guide refresh --deterministic` updates the index from `H1`/`H2` headings and opening lines. Each confirmed update automatically re-runs `wiki render`.

### Optional Off-Peak `Context Maintenance` and Deterministic Lint Fallback
Disabled by default, and enabled opt-in via OS `launchd`/`cron` or platform scheduler over an explicit Notion `Capture Inbox` ID (never reading local platform chat logs), throttled to 1 req/s, concurrency 1, and bounded to `--max-pages 200` per run.

- **Mode A (Deterministic Lint, Default and Zero-LLM Fallback):** Runs bounded Notion-wins `Context Sync`, then runs deterministic checks across confirmed DBs for missing `extra_required_fields`, broken relations, stale records past user-configured `stale_after` (`okf validate --stale` and `notion-cli-agent validate check`), zero-LLM trigram+tag near-duplicate candidates (`lore/src/core/conflict.ts:80-100`, `pairLimit: 50`), and unreferenced `Capture Inbox` inventory (`karpathy-llm-wiki/scripts/check_evidence.py:15-16`). Writes a concise **Maintenance Run Summary** locally and optionally appends it additively to a user-chosen Notion log page.
- **Mode B (Opt-In Off-Peak LLM-Assisted Maintenance):** Feeds Mode A's bounded candidate pack to the user's configured off-peak LLM or scheduled external agent calling the CLI. Every write passes through `core/`, where validated additive updates run autonomously, while every `Destructive Action` or schema edit halts into `pending_proposals` and appears in the Maintenance Run Summary for out-of-band human `wiki approve <proposal_id>`.

## 6. Pre-Commitment Guard Inputs (`grazi-tunnel-vision-guard`)

Bring these 6 counterarguments, hidden complexity risks, and blocking checks into `grazi-tunnel-vision-guard` before locking `DESIGN-DOC.md`:

1. **Over-engineering SQLite vs atomic JSON in v1.0:** For 15 to 25 core databases (<150 KB total metadata), `ontology.yaml` + atomic `cache.json` + `lore`-style atomic `rate-limit-state.json` (Option 3B) covers roughly 90% of Option 3A's value with zero database driver concerns. *Guard question:* Do cross-process 429 leases, concurrent Level 2 fractal writes, and Portuguese/accented FTS5 justify SQLite in v1.0 (using built-in `node:sqlite` or pure-Go `modernc.org/sqlite`), or should v1.0 start on atomic JSON and introduce SQLite only if record-stub caching is added?
2. **Coupling to `ntn` vs maintaining a direct Notion REST client:** Avoiding `ntn` eliminates a subprocess bottleneck, removes a third-party binary dependency, and fixes HTTP 429 handling plus page-scoped auth, but means maintaining our own small Notion HTTP client (`2025-09-03` + `2026-03-11` + Views API) and token storage. *Guard question:* Should we build a thin wrapper over the official `@notionhq/client` Software Development Kit (SDK) vs raw `fetch`, while keeping `ntn` strictly rejected?
3. **Unverified live Notion REST behavior on native Wiki roots and Views API (run before Design Doc):** Static docs confirm `GET /v1/blocks/{id}/children` marks linked views `unsupported` and `GET /v1/views?data_source_id=...` returns linked views, but neither endpoint has been tested live against the author's native Wiki root (`$NOTION_ROOT_ID`). *Guard action:* Run a 15-minute, 5-call live API spike (`GET /v1/databases/{root}`, `GET /v1/blocks/{root}/children`, `POST /v1/search` for `data_source`, `GET /v1/views?data_source_id=...`, `GET /v1/pages/{guide}/markdown`) before finalizing `DESIGN-DOC.md`.
4. **Dual CLI + MCP scope creep:** Maintaining CLI and MCP simultaneously burdened `lore`, and 4 MCP tools sit close to the 1,500-token ceiling. *Guard question:* Confirm locking v1.0 to **CLI + `SKILL.md` + `wiki render` only**, deferring the optional thin MCP adapter to v1.1 unless a concrete tester friend cannot run shell tools.
5. **Level 0 double-injection drift and shell security reality:** Writing Push blocks across multiple host files while also enabling `SessionStart` hooks would double-inject Level 0 context and breach 1,500 tokens, while any shell-capable agent without host command-ask rules or separate Notion integration tokens can attempt to bypass local config files. *Guard question:* Enforce one canonical injection mode per profile (verified by `wiki doctor`) and state clearly in user docs what is platform-enforced (Notion internal integration page sharing, out-of-band `wiki approve`, harness `ask` rules) vs operational governance (`WIKI_AGENT_PROFILE` lock).
6. **Over-fitting to the author's 61-schema Wiki:** Tester friends may start with 4 databases on a plain page and zero guide pages, or 40+ confirmed databases that exceed a 400-token flat Level 0 catalog. *Guard question:* Define a concrete Level 0 overflow rule (for example, summarize by `Taxonomy` area above 30 confirmed databases and expand area databases on demand) and validate `wiki setup` early on both a minimal blank workspace and a multi-hub workspace.
