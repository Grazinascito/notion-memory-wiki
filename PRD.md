# Notion Memory Wiki — PRD

> Status: ready for Design Doc · Started: 2026-11-22 · Reviewed: 2026-11-22

## 1. Executive Summary
We're building Notion Memory Wiki, a platform-agnostic and LLM-agnostic Context System over Notion with bounded two-level `Root Page` setup, three-level `Progressive Disclosure`, per-agent `Agent Scope`, deterministic `Validation`, Notion-wins `Context Sync`, and optional off-peak `Context Maintenance`, for individual technical users and early tester friends operating one or multiple specialist AI agents, to solve the lack of a persistent, structured shared context space where agents can read, route, and update workspace knowledge without pasted links, blind discovery, context rot, or background LLM quota contention. This will result in 90% or higher link-free Notion task accuracy within 30 days, initial setup time falling from 28 minutes to under 5 minutes, zero HTTP 429 errors caused by the memory layer during active chats, and total Level 0 startup context kept under 1,500 tokens instead of 15,000 to 25,000+ tokens.

## 2. Problem Statement
- **Who has this problem:**
  In version 1, the primary focus is an individual user who uses AI agents for knowledge work beyond software code, running one or multiple personal agents over the same Notion workspace. This also includes early tester friends who need to run the same portable setup over their own Notion workspaces, agent platforms, and LLM, meaning Large Language Model, providers.
- **What is the problem:**
  The root problem is the lack of a Context System, a central structured space in Notion that allows agents to accumulate knowledge and learn together over time. Without this structured, agent-readable space, four recurring failures appear:
  1. Agents fail to keep up with ongoing work the way a teammate would, so the user has to repeat background context in every session.
  2. Information stays scattered across disconnected tools or buried inside workspaces that agents navigate poorly, causing the user to hesitate before asking an agent questions it should be able to answer.
  3. AI usage stays stuck in isolated chatbot sessions and one-off demos, creating activity without durable progress or shared memory across sessions and across different specialist agents.
  4. When multiple agents operate in parallel, basic governance is missing to respect user-chosen access boundaries, prevent autonomous external actions by the memory layer, and require explicit user approval before destructive actions or schema changes, meaning changes to database columns or properties in Notion.
- **Why it is painful** (user impact + business impact):
  Knowledge produced in each session disappears inside isolated chat histories instead of compounding over time. The user spends repeated effort re-explaining background context, avoids delegating ambitious workflows, and falls back to fragile local workarounds or loose folders of plain files that discard data structure. When the user tries to patch this gap with parallel local memory graphs driven by background LLM calls, or with raw integrations that load dozens of tools into every prompt, machine load spikes, conversation context degrades, and active chats still fail without solving the core problem.
- **Evidence** (quotes, analytics, support tickets):
  - Core problem framing adopted by the author from Notion's *A New Shape for Work* field guide (verbatim quotes preserved):
    - `"Your AI has so much trouble finding things that you find yourself hesitating to ask it questions that it should (at least in theory) be able to answer. You have the feeling that information is too disorganized, spread across too many systems, or locked up in legacy tools that don’t work well with agents."`
    - `"You constantly have to catch up your agent and give it background information because it’s missing key context; it can’t just 'keep up' the way a teammate would."`
    - `"There is a lot of one-off use of chatbots on your team, and the occasional flashy demo, but not nearly as much reliable, systematic automation of business processes and functions as you’d like. You see a lot of motion, but not as much durable progress."`
    - `"These may seem like separate problems, but in reality, they all point toward a single cause: the lack of a context system. A context system is what allows your team’s agents to learn together over time."`
  - Documented failures of previous attempts to solve this gap (author's 2026-11-21 technical diagnosis):
    - Local memory graph plugin (Cognee): failed to solve the core Context System gap while consuming 462.5% CPU and 1.2 GB of disk space and triggering HTTP 429 rate-limit errors. It shared `GLM_API_KEY` with active chats, sent transcripts automatically on session end or compression (`improve_on_end: true`), fired 7 or more parallel LLM calls without rate limiting (`llm_rate_limit_enabled: False`) with burst retries (`8s, 16s, 32s, 64s`), generated embeddings on local CPU, and maintained 3 local databases trying to rebuild via LLM a graph that Notion already stores natively.
    - Official Notion MCP, the Model Context Protocol integration exposing tools to agents: loaded 77 tools and added roughly 15,000 to 25,000 or more static prefix tokens on every turn, causing context rot, the degradation where excess fixed text makes the agent forget recent instructions.
    - Unguided Notion API access and flat ingestion: without prior workspace knowledge, each agent burned multiple API calls at the start of every task just to discover databases, IDs, columns, valid select or status options, and relations. Recursive block-by-block page ingestion sent roughly 2,000 HTTP requests and flattened structured databases into plain text.
    - Real LLM provider concurrency constraint observed on the Z.AI Coding Plan account: models `glm-5.3`, `glm-5-turbo`, and `glm-5.3-flash` share a single concurrency limit and cascade-fail with HTTP `429 (1302)` in roughly 1 second whenever background work competes with active chats.
  - Empirical full-extraction benchmark without scope limits (author's live test on 2026-11-22 against her Notion Wiki):
    - Asking a chat agent to extract the complete taxonomy and ontology took **28 minutes** and produced `docs/wiki-raw-extraction-2026-11-22.json` (**875 KB**) from **126 raw Notion calls** (`108` `notion-fetch` and `18` `notion-query-data-sources`), covering `45` pages, `7` database blocks or linked views, `55` full `data_source` schemas with properties and options, `18` row queries (including duplicate or legacy databases), and one `404` error on `Weekly Log`. The extraction also showed that the Wiki root itself is a Notion wiki database (`type: database`, `wiki: true`) and that most core databases (`Projects`, `Goals`, `Results`, `Resources db`, `Entries`, `Tasks`) sit inside top-level hub pages (`Project management`, `Goals e OKRs`, `Resource Library`, `Daily & Wellbeing`, `Inbox`) or linked views rather than directly at level 1.
  - Personal hours-lost measurements and direct external user interviews: `evidence missing` (external problem validation is anchored on Notion's *A New Shape for Work* field guide).

## 3. Target Users & Personas
### Primary persona
- **Role / context:**
  An advanced individual technical user, starting with the author, who uses Notion as a second brain containing a native Wiki with an 8-page `Agent Operating Guide` plus structured databases (both directly on the home page and nested inside top-level hub pages) for projects, tasks, inbox, notes, resources, meetings, habits and health, executive dysfunction, career, job applications, contacts, companies, and operating rules, while running multiple specialist agents or profiles in parallel.
- **Tech level:**
  Advanced technical user comfortable installing, configuring, and operating agent platforms locally, including Hermes, OpenClaw, OpenBot, Grok Bot, Claude Code, Codex, and Cursor, across multiple LLM providers.
- **Goals:**
  Connect all specialist agents to the same Notion Context System so knowledge compounds across sessions, each agent navigates the workspace ontology and updates the right records using fewer tokens, and user-defined access limits hold without interrupting active conversations.
- **Pain points:**
  Lost context across isolated chats, repeated manual re-explanation of background details, agents starting blind to Notion's real structure, and failures in earlier workarounds such as background local memory graphs causing HTTP 429 errors or bloated tool lists causing context rot.
- **Current behavior / workaround:**
  Palliative cleanup applied in Hermes after removing Cognee: local file-based memory (`MEMORY.md`, `USER.md`, `state.db`) was re-enabled, retry count was raised to 6, and auxiliary or research tasks were shifted to faster models.

### Secondary personas (if any)
- **Individual technical tester friends:**
  Technical or intermediate-technical users who already run at least one agent platform, such as Claude Code, Cursor, Codex, Hermes, or OpenClaw, and want to connect their agents to their own Notion workspace using their own LLM provider and zero extra LLM keys inside the memory layer. They differ from the primary persona by needing a portable setup that adapts to each user's existing Notion ontology without forcing database renames or mandatory pre-existing guide pages, plus an optional recommended starter ontology and base `Agent Operating Guide` template for users starting from scratch.

- **Competitive landscape** (optional):
  Market comparison conducted on 2026-11-22 across local, cloud, and hybrid agent memory and context systems:
  - **Notion Lore (`makenotion/lore`), cloud over Notion:** Notion's official MIT open-source shared memory layer for agents like Claude Code, Codex, and Cursor using five fixed relational databases (`Projects`, `Topics`, `Memories`, `Entities`, `Facts`). Author decision: do not adopt or depend on `Notion Lore`, using it only as an implementation reference for the Design Doc, because it imposes a fixed five-database schema rather than mapping a user's existing Wiki ontology and `Agent Operating Guide`.
  - **Native Notion Agents and official Notion MCP, cloud over Notion:** Native Notion Agents run inside Notion but stay locked to Notion's internal environment instead of serving external agents across any platform and any LLM provider. The official MCP loads 77 tools and added 15,000 to 25,000+ static tokens per turn in the 2026-11-21 diagnosis, causing context rot.
  - **LLM Wiki with Obsidian as a Knowledge Graph (Karpathy `LLM Wiki` pattern + Obsidian), local-first:** Local Markdown files versioned in Git with `[[wikilinks]]`, visual graph browsing, and agent-maintained synthesis across `raw/`, `wiki/`, and schema instructions. Genuine strengths: full local ownership, instant speed with zero API rate limits, strong fit for coding agents, and Git history. Key trade-offs: lacks Notion's native relational databases, typed columns, views, and rollups; mobile access and collaboration need extra layers; ongoing wiki maintenance still relies on LLM calls.
  - **Hindsight (Vectorize), hybrid cloud and self-hosted:** Dedicated agent memory layer separating world facts, agent experiences, observations, and evolving mental models, with hybrid search, locally mountable Markdown pages (`Hindsight Pages`), lightweight dedicated models, and wide compatibility including Hermes, OpenClaw, Claude Code, Codex, and Cursor. Key trade-offs: requires self-hosted infrastructure or managed cloud plus model inference for ingestion and consolidation, and operates as a memory backend rather than replacing Notion as a human-first daily relational workspace.
  - **Mem0 and Supermemory, hybrid cloud, self-hosted, or local binary:** Dedicated agent memory and user-profiling APIs offering low latency, per-user and per-agent isolation, and connectors (Supermemory syncs sources including Notion, Drive, and GitHub and offers an LLM-free document retrieval mode). Key trade-offs: both serve as programmatic backends for agents rather than human-editable workspaces with Wikis and relational databases.
  - **Zep and Graphiti, enterprise cloud or self-hosted graph database:** Bi-temporal knowledge graphs that track when facts became true and when they were superseded while ingesting from Notion, Slack, Drive, and Gmail. Key trade-offs: Graphiti requires operating a graph database and LLM extraction pipeline, and Zep is an enterprise paid context layer aimed at governed reads rather than direct human authoring.
  - **Letta (formerly MemGPT), local or cloud with Git-backed context repositories:** Stateful agent platform where agents edit their own Git-versioned Markdown memory and run background consolidation. Key trade-off: coupled to Letta's own agent runtime, conflicting with the platform-agnostic premise.
  - **Local background LLM memory graph plugins (such as Cognee):** Tested and discarded on 2026-11-21 after hitting 462.5% CPU, 1.2 GB disk usage, and HTTP 429 rate-limit failures while trying to reconstruct via LLM a graph Notion already holds natively.
  - **Explicit strategic trade-off decision:** We maintain our single commitment to Notion as the human-editable structured source of truth for its native relational databases and daily workflow usability. We knowingly give up Obsidian's pure local-file speed and dedicated temporal engines like Hindsight or Zep, while requiring lightweight learned workspace navigation and synchronization in our product without bloating agent context.
  - **Notion ecosystem conceptual references:** Notion Field Guide *A New Shape for Work* on Shared Context Systems and Syncs, Notion Developer Platform Syncs, and Notion Workers Syncs Guide.

## 5. Solution Overview
- **What we're building:**
  Notion Memory Wiki is a Context System over Notion that lets any external agent, running on any agent platform and any LLM provider, navigate, query, and update the user's Notion workspace without pasted page links, without context rot, and without requiring any internal LLM API key inside the memory layer itself. It preserves Notion as the single source of truth, combining structured databases, organized unstructured pages, and live traversal of Notion's native `Knowledge Graph` relationships.

Because of the data’s structure, they get the right answers more often, faster, and using fewer tokens. This structure also unlocks smaller models’ ability to perform more ambitious tasks for you.   Product premises and behavioral guarantees:
  - **Single source of truth in Notion:** Notion is the canonical store for all durable knowledge, schema definitions, and page content; whenever local cached metadata drifts from Notion, Notion always wins.
  - **Platform-agnostic and zero mandatory internal LLM:** Any agent platform and any LLM provider can connect, with zero hardcoded database IDs, fixed database names, or personal bot names. Core memory operations (reads, writes, deterministic `Validation`, `Progressive Disclosure`, `Agent Scope`, and structural `Context Sync`) require zero internal LLM calls and zero dedicated LLM API key inside Notion Memory Wiki; all reasoning stays inside the user's connected agent, and optional AI-assisted review in `Context Maintenance` can stay disabled or run deterministic-only checks when no LLM is configured.
  - **Recommended `Agent Operating Guide` delivered via `Progressive Disclosure`:** Workspaces with orientation pages, such as the author's 8 pages tagged `Agent Operating Guide` (Onboarding Guide, User about, Mission, Vision, Values, Team Directory, Work Guidelines, Processes/SOPs, Vacilos db, and Decisions), expose a concise startup summary plus an index of when to open longer pages on demand. The concise summary is produced during setup (and refreshed only when a guide page changes) by the user's connected agent or edited directly by the user, avoiding silent background LLM calls. If a new workspace has no `Agent Operating Guide` yet, setup still succeeds cleanly and offers an optional starter template created only with user confirmation.
  - **Clear separation between internal maintenance and external business workflows:** Notion Memory Wiki owns `Context Sync` and optional off-peak `Context Maintenance`, while each user's specialist agents and external platforms build and run business or routine automations on top. Conversational facts mentioned during chat are persisted to Notion only when explicitly requested during the chat or when the user or agent deposits a note into the designated Notion `Capture Inbox` for off-peak `Context Maintenance`, avoiding silent transcript scraping.
  - **Clear access boundaries and explicit safety definitions:** The overall workspace boundary is defined by the user's `Root Page` (accepting either a regular Notion page or a native Notion Wiki database with `wiki: true`) plus any user-approved linked views shared with the Notion integration. On top of that boundary, optional `Agent Scope` provides an application-level operational filter controlling which areas and databases each `Specialist Agent` can see at Level 0, read, write, or traverse across relations, with zero hardcoded private categories; strict credential-level isolation remains available via Notion's native sharing permissions. The `Agent Operating Guide` is readable across agents by default unless the user explicitly excludes specific guide pages from an agent's `Agent Scope`. The memory layer blocks all `Autonomous External Actions` (side effects outside the authorized Notion workspace and active user conversation, such as emailing, messaging third parties, or mutating other SaaS tools) and requires explicit user approval before any `Destructive Action` (deleting or archiving pages or records, clearing populated properties, or overwriting existing non-empty user prose, while allowing additive writes and routine structured updates such as changing status, tags, dates, or relations) or Notion schema change.
  - **Strict 3-level `Progressive Disclosure` under a measurable token budget:** Total Level 0 startup context stays under **1,500 tokens** (covering the Level 0 database catalog, concise `Agent Operating Guide` summary and index, and the exposed tool or interface surface). Long Notion IDs, full column lists, status options across all databases, and per-record fractal sub-databases stay outside the LLM's initial context window and are resolved on demand by Notion Memory Wiki.

- **How it works** (steps from the user's point of view):
  1. **Bounded two-level setup from the `Root Page`:** The user provides the link to their `Root Page` (either a standard page or a native Notion Wiki database). Setup performs a bounded scan up to two levels deep without reading row contents: top-level pages and databases directly on the `Root Page`, plus core databases embedded inside top-level hub pages (such as `Project management`, `Goals e OKRs`, `Resource Library`, `Daily & Wellbeing`, and `Inbox`) and linked views referenced there. Using the user's connected agent (or a deterministic structural scan plus manual review when no agent or LLM is used), setup proposes the `Taxonomy`, core `Ontology`, and `Agent Operating Guide` summary. The user confirms active core databases and linked views while explicitly excluding legacy or duplicate databases, and can optionally declare extra required fields per database beyond Notion's native schema. Users starting from scratch can opt into a recommended starter ontology and base `Agent Operating Guide` template. (Packaging setup as an agent skill is logged as a Design Doc hypothesis.)
  2. **Three-level `Progressive Disclosure` on agent startup and operation:**
     - **Level 0 (loaded at startup, under 1,500 tokens total including tool definitions):** Only a short catalog listing names and purposes of the core databases permitted by the agent's `Agent Scope` (no Notion IDs, no column lists, no status options, no per-record fractal sub-databases), paired with the concise `Agent Operating Guide` core summary and an index telling the agent when to open longer pages such as `Processes (SOPs)` or `Decisions`.
     - **Level 1 (single destination on demand):** When the user asks a question or requests an update, the agent picks the target from the Level 0 catalog and requests only that target. Outside the LLM prompt, Notion Memory Wiki translates the short name to the real Notion identifier, checks that single database's schema and valid options, traverses permitted relations on demand, and returns only the requested records while all other databases remain outside the conversation.
     - **Level 2 (`Fractal Structure` on demand):** Local or one-off databases nested inside individual database records or deep sub-pages (such as a draft tracker inside one specific project row) cost zero tokens while the conversation covers other topics and enter context only when the agent opens that specific record or page.
  3. **Link-free reading, writing, and routing:** The user gives natural requests and the agent reads or writes to the right destination using the workspace `Ontology` and native `Knowledge Graph` relations. Verbatim real scenarios supplied by the author:
     - Direct capture to the right database: `"adicione esse link em resources https://www.notion.com/a-new-shape-for-work#what-is-the-new-shape-for-work "` (add this link to Resources).
     - Status-filtered structured query: `"quais projetos em progresso atualmente?"` (which projects are currently in progress?), where the agent knows the exact target database (`Projects` inside `Project management`) and status property.
     - Direct goals query: `"quais são minhas metas atuais?"` (what are my current goals?), querying `Goals` inside `Goals e OKRs` without a pasted link.
     - Research and structured multi-field entry: `"olha o link dessa vaga aqui, vou me inscrever, procure pelo menos contatos que divulgaram essa vaga ou com potencial"` (given this job link, the user's external agent researches contacts and records them with descriptions in the Contacts database linked to the job).
     - Consumption by a user-scheduled external agent routine: `"quero ter um cronjob que toda semana o agente varre as paginas de daily log da semana em especifico e traga as principais dores e queixas e me mande e tb adicione na pagina de problems map"` (the user's own weekly job scans that week's `Daily & Wellbeing` entries, summarizes top pains, sends them to the user via the user's platform, and writes the validated update into `Personal Troubles Map`).
  4. **Progressive `Fractal Structure` learning and Notion-wins `Context Sync`:** Whenever an agent opens a specific record containing a nested sub-database, the system discovers that Level 2 branch on demand and stores its pointer in the workspace map. When schemas, options, or guide pages change in Notion, `Context Sync` refreshes the workspace map automatically on mismatch plus via scheduled or on-demand refresh, with Notion always winning on drift.
  5. **Optional off-peak `Context Maintenance`:** When enabled by the user, a scheduled routine running strictly outside active chat hours reviews stale pages already inside the `Root Page` and processes notes explicitly deposited by the user or agents into a designated Notion `Capture Inbox` (never reading platform-specific local chat logs). It autonomously applies only validated additive updates and logs any proposed `Destructive Action` (such as deleting, archiving, or overwriting existing user prose) into a concise run summary for the user to approve later.

- **Key features:**
  1. **Bounded two-level setup from a `Root Page` or native Notion Wiki:** Maps top-level objects plus core databases inside top-level hub pages and user-confirmed linked views, skips row contents and user-excluded legacy or duplicate databases, and offers an optional starter ontology and `Agent Operating Guide` template.
  2. **Ontology and `Knowledge Graph` navigation with 3-level `Progressive Disclosure` and `Agent Scope`:** Enables any agent on any platform to read, filter, write, and traverse permitted cross-database relations without manual links, keeping total Level 0 startup context under 1,500 tokens and enforcing `Agent Scope` on both direct access and relation traversal.
  3. **Notion-wins `Context Sync`:** Keeps `Taxonomy`, `Ontology`, learned Level 2 fractal pointers, and the `Agent Operating Guide` index aligned with Notion without blind rediscovery or active-chat LLM quota contention.
  4. **Deterministic `Validation` and explicit safety guardrails:** Validates writes without LLM calls against Notion's native schema (title, property types, valid select, multi-select, and status options, read-only guards, and relation target databases) plus any extra required fields declared by the user in the `Ontology`, while blocking `Autonomous External Actions` and requiring explicit user approval before any `Destructive Action` or schema change.
  5. **Optional off-peak `Context Maintenance`:** Opt-in scheduled maintenance over Notion pages and an explicit Notion `Capture Inbox`, applying only validated additive writes autonomously, queuing proposed destructive edits into a concise run summary, and falling back to deterministic checks or disabled mode when no LLM is configured.

  **Relationship with `Factories` and `Specialist Agents`:** Notion Memory Wiki provides the shared Context System foundation so multiple `Specialist Agents` configured by the user on any platform (such as separate Grok Bot or Hermes agents for projects and tasks, research into `Resources db`, and health and wellbeing `daily log` and `weekly review` routines) collaborate on the same `Knowledge Graph`, populate typed properties, and link records across databases following the `Team Directory`. Each specialist's prompts, business workflows, web searches, notifications back to the user, and schedules live in the user's agent platform, while Notion Memory Wiki guarantees `Ontology`, `Progressive Disclosure` filtered by `Agent Scope`, deterministic `Validation`, and safety guardrails.

  **What is deliberately simple in v1:** Operational per-agent isolation uses simple area or database selection (`Agent Scope`) over the `Root Page` and native Notion sharing (no enterprise multi-human RBAC); `Context Maintenance` operates only over Notion pages and an explicit Notion `Capture Inbox` with a concise summary log (no local chat log scraping and no interactive diff UI for routine non-destructive edits); no hardcoded business workflows live inside the product; and no built-in `External Sync` connectors for third-party apps are included.

- [ ] Total Level 0 startup context (database catalog, concise `Agent Operating Guide` summary and index, and exposed tool definitions) stays under 1,500 tokens, with no Notion IDs, no column lists, no status options, and no per-record fractal sub-databases.
- [ ] The `Agent Operating Guide` loads progressively, exposing a concise user-edited or setup-generated core summary plus an index of when to open longer pages like `Processes (SOPs)`, `Team Directory`, or `Decisions`.
- [ ] When an `Agent Scope` is configured for a `Specialist Agent` (such as limiting one agent to health and wellbeing), Level 0 exposes and authorizes only the areas and databases inside that scope; `Agent Operating Guide` pages remain readable across agents by default unless explicitly excluded from that agent's scope.
- [ ] Integration stays platform-agnostic across Hermes, OpenClaw, OpenBot, Grok Bot, Claude Code, Codex, Cursor, and other platforms without hardcoded bot names.

**Story 3: Link-free structured queries across `Ontology`, `Knowledge Graph`, and `Fractal Structure`**
As a user asking natural questions in chat, I want to ask things like `"quais projetos em progresso atualmente?"` or `"quais são minhas metas atuais?"` without pasting Notion links, so that the agent retrieves exact answers using fewer tokens and zero blind discovery calls.
- [ ] At Level 1 on demand, once the agent picks a destination from the Level 0 catalog, Notion Memory Wiki translates the short name to the real Notion identifier outside the LLM prompt, inspects schema and valid options for that single database only, and returns only the requested records.
- [ ] All other databases in the workspace remain outside the agent's context window during the query.
- [ ] At Level 2 on demand, when the agent opens an individual database record or deep sub-page containing nested `Fractal Structure` databases, the system discovers that branch on demand and stores its pointer in the workspace map while spending zero tokens before that record is opened.
- [ ] Agents traverse native `Knowledge Graph` relation links across connected databases without manual URLs, while blocking traversal into any target database outside the agent's configured `Agent Scope`.

**Story 4: Capture, routing, cross-database linking, and deterministic `Validation`**
As a user saving new knowledge or connecting records in Notion, I want to trigger actions like `"adicione esse link em resources..."`, log job contacts with descriptions, or link resources and tasks to a project, so that data lands in the right database cleanly and safely.
- [ ] The agent selects the right destination database using the `Ontology`, fills typed properties, and creates valid cross-database relations such as linking `Resources db` items and tasks to a project or linking contacts to a job entry.
- [ ] Before writing to Notion, deterministic `Validation` runs with zero LLM calls to verify Notion's native schema rules (title present, valid property types, valid select, multi-select, and status options, read-only property protection, and valid relation target database), target allowance under `Agent Scope`, and any user-declared required fields in the `Ontology`.
- [ ] When a write fails deterministic `Validation`, the system rejects the invalid write and returns the exact failure reason plus the valid options for that single destination so the agent can self-correct.
- [ ] Any `Autonomous External Action` attempted by the memory layer is blocked, and any `Destructive Action` (deleting or archiving records, clearing populated properties, or overwriting existing non-empty user prose) or Notion schema change requires explicit user approval before execution.

**Story 5: Collaboration across multiple `Specialist Agents` and external user workflows**
As a user operating multiple specialist agents and scheduled personal routines, I want different agents to read and write to the same Context System following `Processes (SOPs)` and `Team Directory`, so that one specialist's outputs feed another without hardcoding workflows inside the memory layer.
- [ ] One specialist agent can discover and link records created by another specialist in the same workspace, such as a Projects agent linking items previously cataloged by a Research agent in `Resources db`.
- [ ] An external user-scheduled workflow, such as a weekly cronjob scanning `Daily & Wellbeing` entries for a specific week, sending the summary to the user via the user's platform, and appending top pains to `Personal Troubles Map`, operates cleanly through the Context System under `Ontology`, `Agent Scope`, and `Validation`.
- [ ] Any read, write, or relation traversal outside a specialist agent's configured `Agent Scope` is clearly rejected.
- [ ] Any agent on any platform can deposit a quick note or session takeaway into the user's designated Notion `Capture Inbox` during active chat for later off-peak consolidation.

**Story 6: Notion-wins `Context Sync` and optional off-peak `Context Maintenance`**
As a user whose workspace evolves every day, I want the workspace map to stay synchronized with Notion and have an optional off-peak routine to process captured notes and flag stale pages, so that the system stays accurate without disrupting active chats.
- [ ] `Context Sync` refreshes `Taxonomy`, `Ontology`, learned Level 2 fractal pointers, and the `Agent Operating Guide` index whenever Notion schema drift is detected as well as on scheduled or on-demand refresh, with Notion always winning on conflict.
- [ ] The user can enable or disable optional `Context Maintenance`, configure its off-peak schedule, and choose which Notion page or database serves as the `Capture Inbox`.
- [ ] When enabled, `Context Maintenance` operates only on Notion pages inside the `Root Page` and items deposited in the `Capture Inbox` (never scraping local platform chat logs), autonomously executing only validated additive writes and recording any proposed `Destructive Action` or schema change in the run summary for explicit user approval.
- [ ] Every `Context Maintenance` run produces a concise execution summary of additive updates applied and destructive or structural proposals awaiting approval.
- [ ] Neither `Context Sync` nor `Context Maintenance` triggers concurrent bursts that cause HTTP 429 errors or heavy CPU and disk spikes during active chats; when no LLM is configured for maintenance, `Context Maintenance` runs deterministic checks only or stays disabled while all core features remain operational.

### Constraints & edge cases
- Respect the `Root Page` boundary (including native `wiki: true` roots and user-approved linked views), native Notion sharing permissions, and each specialist agent's `Agent Scope` across direct reads, writes, and `Knowledge Graph` relation traversals, with zero hardcoded private categories.
- Block all `Autonomous External Actions` initiated by the memory layer; external web research and user notifications belong exclusively to the user's external agent platform.
- Require explicit user approval before any `Destructive Action` (deleting or archiving pages or records, clearing populated properties, or overwriting existing non-empty user prose) or Notion schema change.
- Require zero internal LLM calls or dedicated LLM API keys for core memory operations (reads, writes, `Validation`, `Progressive Disclosure`, `Agent Scope`, and structural `Context Sync`), maintaining full portability across agent platforms and LLM providers with zero hardcoded database IDs or personal bot names.
- Support workspaces with or without an `Agent Operating Guide`, loading orientation pages via `Progressive Disclosure` (concise setup-generated or user-edited summary plus index) when present and offering an optional starter template when absent.
- Enforce strict 3-level `Progressive Disclosure` keeping total Level 0 startup context under 1,500 tokens (including exposed tool definitions), forbidding the Design Doc from dumping Notion IDs, full column lists, status options across all databases, or per-record fractal sub-databases into initial agent context.
- Enforce bounded two-level initial setup (top-level items plus core databases inside top-level hub pages and user-confirmed linked views, zero row queries) to stay under 5 minutes and avoid unbounded 28-minute, 126-call crawls over legacy or duplicate databases.
- Enforce Notion-wins conflict resolution in `Context Sync`, refreshing drifted schemas automatically without overwriting Notion's structure with stale cached metadata.
- Apply deterministic `Validation` before every write against Notion's native schema plus optional user-declared required fields in the `Ontology`, with zero LLM calls.
- Restrict optional `Context Maintenance` to configured off-peak schedules over Notion pages and the explicit Notion `Capture Inbox`, applying only additive writes autonomously, queuing proposed destructive changes in a concise run summary, controlling request rates to prevent HTTP 429 errors, and supporting deterministic-only or disabled mode when no LLM is configured.

## 8. Out of Scope
- Adopting or depending on `Notion Lore` (`makenotion/lore`), which stays strictly as an external implementation reference for the Design Doc.
- Real-time continuous surveillance or scraping of local platform chat log files (as Cognee did), because it couples the product to each agent platform's internal log format and recreates noise and LLM quota contention; v1 processes only explicit writes and notes deposited into the Notion `Capture Inbox` during optional off-peak `Context Maintenance`.
- Built-in `External Sync` connectors pulling third-party apps such as calendar, email, or Slack into Notion, which remain the responsibility of Notion's own Syncs or separate tools.
- Multi-human team collaboration and enterprise RBAC governance across multiple human teammates, because v1 validates single-owner multi-agent usage and isolated friend setups using `Root Page`, native Notion sharing, and application-level `Agent Scope`.
- Visual setup experience designed for non-technical users unfamiliar with agent platforms, because v1 targets technical and intermediate-technical users.
- Interactive preview or diff-approval UI for routine non-destructive additive edits in Notion, because v1 places explicit approval gates on `Destructive Actions` and schema changes.
- AI-based semantic content validation (such as judging whether a product memo answers all expected questions or automatically propagating a decision across multiple prose pages), keeping v1 focused on deterministic structural `Validation`.
- Hardcoded business automations or turnkey team `Factories` (such as morning briefs, slide deck factories, bug fix factories, or fixed Kanban workflows), because each user's specialist agents build and run their own automations on top of the Context System. Internal `Context Sync` and optional off-peak `Context Maintenance` remain in scope.
- Technical implementation decisions (local database choice, libraries, ports, protocols, proxy architecture, or packaging mechanisms), which belong to the Design Doc after this PRD.

## 9. Dependencies & Risks
- **Dependencies** (technical, external, team):
  - Pre-Design-Doc study on ontology definition and modeling, followed by running the `/grazi-tunnel-vision-guard` pre-commitment gate to compare real alternatives before locking in an ontology approach.
  - Reference-only review of `Notion Lore` (`makenotion/lore`) before the Design Doc, without adopting it as a dependency.
  - Notion API availability, rate limits, native Wiki database support, and workspace sharing permissions.
  - Each user's existing Notion account, chosen agent platform, and optional LLM provider.
- **Risks & mitigations:**
  - **Risk 1 (quota contention or noisy "bad context" from `Context Maintenance`):** Off-peak maintenance could still trigger HTTP 429 errors or corrupt real Notion pages. Mitigation: opt-in only, strict off-peak schedule with rate limiting, scoped only to Notion pages and the explicit `Capture Inbox`, additive-only autonomous writes with deterministic `Validation`, destructive proposals held in the run summary for explicit user approval, and deterministic-only fallback without an LLM.
  - **Risk 2 (slow setup or context rot from unbounded discovery):** Scanning too deeply at setup or exposing too many tools and metadata at startup would recreate the 28-minute crawl or 15,000+ token context rot. Mitigation: bounded two-level setup with zero row queries and explicit exclusion of legacy or duplicate databases, plus strict 3-level `Progressive Disclosure` capped under 1,500 tokens total at Level 0.
  - **Risk 3 (over-fitting ontology to one workspace):** Designing around the author's personal Wiki structure could break setup for tester friends with different Notion layouts or no `Agent Operating Guide`. Mitigation: pre-Design-Doc ontology study plus `/grazi-tunnel-vision-guard`, zero hardcoded database IDs or names, non-blocking setup when guide pages are absent, and early portable setup validation with tester friends.
